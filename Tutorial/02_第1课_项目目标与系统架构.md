## 2. 项目到底是什么

### 2.1 一句话定义

这是一个运行在 STM32H723 上的 Zephyr USB-to-CAN 网桥：Linux 主机通过 `gs_usb`/SocketCAN 发送和接收 CAN 帧，STM32 负责 USB 协议栈、CAN/FDCAN 外设、缓冲和状态管理。

它不是一个完整的电机运动控制器。当前项目没有额外的“下位机控制板”，电机驱动器内部仍然有自己的控制器，但目标值、控制周期和很多上层策略由 Linux 主机发出。

### 2.2 与传统三层系统的区别

传统结构通常是：

```text
上位机：规划、界面、任务调度
    ↓
下位机：固定周期控制、保护、急停
    ↓
电机驱动器：电流环/速度环/位置环
```

本项目更接近：

```text
Linux 主机：规划 + 控制命令 + 部分实时任务
    ↓ USB
STM32H723：USB-to-CAN 转发、缓存、状态管理
    ↓ CAN/FDCAN
电机驱动器：接收命令并执行内部控制环
```

因此，主机调度延迟、USB 调度、STM32 线程调度和 CAN 总线排队，都会进入最终控制延迟。没有下位机并不代表系统更简单，而是意味着实时性和安全责任更多地暴露在主机到总线的链路上。

## 3. 系统组件和职责

| 组件 | 项目中的对应物 | 主要职责 |
|---|---|---|
| Linux 主机 | SocketCAN、`cansend`、`python-can` | 产生控制命令、接收反馈、运行测试程序 |
| USB 主机控制器 | Linux USB 栈 | 枚举设备、调度控制和批量传输 |
| USB 设备类 | `gs_usb` | 把 USB 设备表现成 Linux CAN 网络设备 |
| MCU 应用 | `src/main.cpp` 和各模块 | 初始化 USB、管理 CAN、启动线程 |
| USB 外设 | `zephyr_udc0` / STM32 OTG_HS 的 FS PHY | 收发 USB 包 |
| CAN 设备 | `can_loopback0`、`fdcan2` | 虚拟回环和真实 CAN 总线 |
| Zephyr 内核 | 线程、消息队列、信号量、日志 | 调度任务并传递状态和数据 |
| 电机驱动器 | 外部 CAN 节点 | 执行命令并返回电机状态 |

本课要特别区分两类“设备”：

- `gs_usb_dev` 是 USB 设备类的逻辑设备。
- `fdcan2` 是 STM32 的真实 CAN 控制器。

它们不是同一个设备，但通过 `gs_usb_register()` 和通道数组连接起来。

## 4. 从工程文件确认架构

### 4.1 板级硬件：`H7_Work.dts`

打开 [H7_Work.dts](../boards/H7_Work/H7_Work.dts)，先只看下面几个节点：

```dts
gs_usb0: gs_usb0 {
    compatible = "gs_usb";
};

can_loopback0: can_loopback {
    compatible = "zephyr,can-loopback";
    status = "okay";
};

zephyr_udc0: &usbotg_hs {
    maximum-speed = "full-speed";
    status = "okay";
};

&fdcan2 {
    pinctrl-0 = <&fdcan2_rx_pb12 &fdcan2_tx_pb13>;
    status = "okay";
};
```

从这段配置可以得出四个事实：

1. 工程声明了一个 `gs_usb` 逻辑设备。
2. 工程声明了一个虚拟 CAN 回环设备。
3. USB 使用 Full-Speed 设备栈。
4. `fdcan2` 是实际接到 PB12/PB13 的 CAN 控制器。

### 4.2 CAN 通道映射：`Basic_USB.cpp`

`src/Basic_USB.cpp` 中的数组是连接逻辑设备和 CAN 设备的关键：

```cpp
const struct device *can_channels[CONFIG_USBD_GS_USB_MAX_CHANNELS] =
{
    DEVICE_DT_GET(DT_NODELABEL(can_loopback0)),
    DEVICE_DT_GET(DT_NODELABEL(fdcan2)),
};
```

当前工程的通道可以理解为：

| 通道 | Zephyr 设备 | 用途 |
|---|---|---|
| channel 0 | `can_loopback0` | 虚拟回环、无外部电机的测试 |
| channel 1 | `fdcan2` | 真实 CAN/FDCAN 总线 |

`CONFIG_USBD_GS_USB_MAX_CHANNELS=2` 规定了最多暴露两个通道。后续分析 Linux 创建的 `can0`、`can1` 时，必须先确认主机编号与设备通道的对应关系，不要只凭名称猜测。

### 4.3 应用入口：`main.cpp`

`src/main.cpp` 有两类内容：

1. 文件顶部通过 `K_THREAD_DEFINE` 创建线程。
2. `main()` 中注册 gs_usb、添加描述符、初始化并使能 USB。

初始化的核心顺序是：

```text
ops.event = gs_usb_event_handler
    ↓
检查 CAN 通道指针
    ↓
gs_usb_register()
    ↓
添加语言、厂商、产品、序列号等描述符
    ↓
添加 Full-Speed 配置并注册 gs_usb class
    ↓
设置 USB 版本和设备版本
    ↓
usbd_init()
    ↓
usbd_enable()
```

只有 `usbd_enable()` 成功后，USB 设备才真正对主机提供可用的设备服务。任何一步返回错误，`main()` 都会记录日志并返回错误码。

### 4.4 线程入口

当前文件中定义了三个已启用线程：

| 线程 | 入口函数 | 优先级 | 主要用途 |
|---|---|---:|---|
| `RTT_TX_tid` | `RTT_TX_thread` | 7 | 从 CAN 消息队列读取数据并进行当前应用处理 |
| `RTT_RX_tid` | `RTT_RX_thread` | 6 | 读取 RTT 命令并切换工作模式 |
| `CAN_loopback_tid` | `CAN_loopback_thread` | 5 | 周期发送虚拟回环报文 |

`CAN2_tid` 和 `USB_CAN_Err_tid` 当前被注释，说明“代码中存在的功能”和“当前固件实际运行的功能”不能混为一谈。阅读嵌入式项目时，一定要检查线程是否真的被创建。

## 5. 两种工作模式

这是本项目最容易被忽略的结构。当前工程不仅有 USB-to-CAN 模式，还有通过 RTT 命令切换到本地 CAN 控制的模式。

### 5.1 模式 A：USB-to-CAN 模式

这是项目的默认目标模式：

```text
Linux SocketCAN
    ↓ USB 控制/批量传输
gs_usb
    ↓ CAN 通道映射
fdcan2
    ↓
电机驱动器
```

在 `main()` 中，`gs_usb_register()` 把 `gs_usb_dev` 与 `can_channels[]` 关联；主机之后可以通过 Linux 的 `gs_usb` 驱动配置 CAN 通道和发送帧。

该模式下要重点观察：

- USB 是否成功枚举。
- Linux 是否创建了预期的 CAN 网络设备。
- 主机设置的 bit timing 是否成功下发。
- `MODE(START)` 是否使对应的 CAN 控制器启动。
- CAN 帧是否从 USB 批量端点进入 FDCAN。

### 5.2 模式 B：本地 CAN 控制模式

在 `src/K_RTT_Thread.cpp` 中，RTT 收到字符 `c` 时调用：

```cpp
M_S_Control.C_M_TO_S(usb_main_get());
```

`C_M_TO_S()` 会：

1. 关闭 USB。
2. 设置本地控制状态。
3. 为各 CAN 通道注册回调、配置过滤器和波特率。
4. 启动 CAN 控制器。

此时 `M_S_Control` 使用的配置表位于 `src/M_S_Control.cpp`：

```cpp
static const uint16_t can_mod_tab[] =
    { CAN_MODE_LOOPBACK, CAN_MODE_NORMAL };

static const uint32_t br_tab[] =
    { 1000000, 1000000 };
```

真实 `fdcan2` 通道使用 `CAN_MODE_NORMAL` 和 1 Mbps。接收回调 `CAN2_RX_Cplt()` 会把数据放入 `basic_can2_q`，之后 `RTT_TX_thread` 可以读取它。

### 5.3 从本地模式返回 USB 模式

RTT 收到字符 `a` 时调用：

```cpp
M_S_Control.C_S_TO_M(usb_main_get(), gs_usb_dev, &ops);
```

`C_S_TO_M()` 会停止 CAN、重新注册 gs_usb 并再次使能 USB。源代码注释已经提示：重新开启端点后，上位机可能仍需要重新寻找 USB 设备。

### 5.4 模式切换的状态图

```text
                 RTT 'c'
USB-to-CAN  ----------------→  本地 CAN 控制
    ↑                              |
    |                              |
    └──────── RTT 'a' ─────────────┘
```

更准确地说，模式切换不是简单地改一个布尔变量，而是同时改变：

- USB 是否 enable。
- CAN 是否由 gs_usb 管理。
- CAN 接收回调由谁注册。
- `M_S_Control::S_State` 的值。
- RTT 线程是否读取 `basic_can2_q`。

## 6. 一帧数据的代码追踪

### 6.1 真实 CAN 接收路径

在本地 CAN 模式下，真实 FDCAN 接收路径可按下面顺序追踪：

```text
fdcan2 硬件收到 CAN 帧
    ↓
Zephyr CAN 驱动触发回调
    ↓
CAN2_RX_Cplt()                  // src/Basic_CAN.cpp
    ↓
k_msgq_purge(&basic_can2_q)
    ↓
k_msgq_put(&basic_can2_q, frame->data, K_NO_WAIT)
    ↓
RTT_TX_thread()                 // src/K_RTT_Thread.cpp
    ↓
k_msgq_get(&basic_can2_q, data, K_FOREVER)
```

要注意：当前回调只把 `frame->data` 的 8 字节 payload 放进队列，没有保存 CAN ID、DLC、帧类型或时间戳。并且回调先 `purge` 队列，因此它表现为“尽量保留最新数据”，而不是“每一帧都可靠保存”。这是后续课程中的重要改进点。

### 6.2 RM 电机发送路径

`src/Extern_RM.cpp` 中的 `Send_RM()` 创建一个 8 字节 CAN 帧：

```cpp
struct can_frame Frame = {
    .id = Id,
    .dlc = 8,
};
```

四个 `int16_t` 电机值被拆成高字节和低字节，然后调用：

```cpp
can_send(can, &Frame, K_NO_WAIT, NULL, NULL);
```

因此，当前应用层协议是：

```text
CAN ID + 4 个 16 位电机值 + 8 字节固定长度
```

本课暂时不判断这种协议是否满足最终控制需求，只先确认数据如何被编码和发送。

## 7. “没有下位机”带来的工程含义

### 7.1 实时性责任上移

没有下位机后，控制周期可能受到以下环节共同影响：

```text
Linux 调度延迟
+ USB 主机调度
+ USB 批量传输排队
+ STM32 USB 线程调度
+ CAN TX 排队
+ CAN 总线仲裁
+ 电机驱动器响应
```

所以不能只看平均延迟。必须关注 p99、p99.9 和最大延迟。一次偶发的长延迟也可能影响高速运动控制。

### 7.2 安全责任不能只交给通信链路

需要提前考虑：

- Linux 程序崩溃时，电机会不会保持上一条命令？
- USB 拔出后，电机驱动器是否会自动停止？
- CAN Bus-Off 后谁负责恢复？
- STM32 重启期间，电机是否仍处于使能状态？
- 是否有心跳、命令超时和独立急停？

这些不是本课立即实现的功能，但它们决定了该项目是否能从“通信实验”发展成“可用的控制系统”。

## 10. 本课容易混淆的地方

### 10.1 `gs_usb` 不是 CAN 控制器

`gs_usb` 是 USB 设备类和协议适配层；真正控制 CAN 外设的是 Zephyr CAN 驱动和 `fdcan2` 设备。

### 10.2 `can_loopback0` 不是外部 CAN 总线

它是虚拟设备，用于测试软件链路。不能用虚拟回环结果直接证明 PB12/PB13、电气收发器和真实电机总线都正常。

### 10.3 “代码里有线程”不等于“线程正在运行”

只有没有被注释、实际执行 `K_THREAD_DEFINE` 的线程才会创建。当前 `CAN2_thread` 和 `USB_CAN_ERR_thread` 是注释状态。

### 10.4 “收到一帧”不等于“保存了完整 CAN 帧”

当前 `basic_can2_q` 的元素是 8 字节数据，CAN ID、DLC 和帧标志没有进入该队列。后续分析时必须区分 payload 和完整 `struct can_frame`。

### 10.5 “平均延迟低”不等于“实时控制可靠”

主机直控系统必须看尾延迟、丢帧、超时和故障恢复，而不是只看平均值。

## 14. 问题记录：当前能否直接控制电机？

### 14.1 控制能力和当前实现状态

这个工程本质上是 USB-to-CAN 网桥，不是完整的电机运动控制器。主机通过 `gs_usb` 向真实 `fdcan2` 发送符合电机协议的 CAN 帧时，可以直接把命令送到电机驱动器；电流环、速度环和位置环仍由电机驱动器内部完成。

工程还提供了本地 CAN 控制入口：RTT 收到字符 `c` 后，`C_M_TO_S()` 关闭 USB 并启动本地 CAN。`Send_RM()` 每次发送一个 8 字节 CAN 帧，其中包含 4 个 `int16_t` 参数（`M_201` 至 `M_204`），所以一次调用最多携带 4 路电机命令。

但当前 `RTT_TX_thread()` 中实际调用的是：

```cpp
Send_RM(DEVICE_DT_GET(DT_NODELABEL(fdcan2)), 0x010, 0, 0, 0, 0);
```

也就是说，当前示例代码发送的是四个零值，并没有把外部输入解析成真正的目标值；因此“具备发送接口”不等于“已经实现完整的自主电机控制器”。软件配置的两个 CAN 通道是 `can_loopback0` 和 `fdcan2`，其中只有 `fdcan2` 是外部 CAN 总线。总线上实际可挂多少个电机取决于电机协议、ID 分配和总线负载，不是由这里的两个通道数直接决定的。

### 14.2 电机反馈实际存放在哪里

当前代码没有保存位置、速度、电流等已解析的反馈变量。真实 `fdcan2` 接收回调 `CAN2_RX_Cplt()` 的路径是：

```text
frame->data
  → basic_can2_q（8 字节消息队列元素）
  → RTT_TX_thread() 的 uint8_t data[8]
```

同类回调还定义了 `basic_canlb_q`、`basic_can1_q` 和 `basic_can3_q`，但当前外部通道实际使用的是 `basic_can2_q`。回调会先执行 `k_msgq_purge()`，因此旧消息可能被清掉；队列中只保存 payload 的 8 个字节，不保存 CAN ID、DLC、帧类型或时间戳。`RTT_TX_thread()` 目前只是打印 `data[0]` 至 `data[7]`，没有进一步解码成反馈变量。

在 USB-to-CAN 主机模式下，反馈由 `gs_usb` 通道直接转发给主机，不能把 `basic_can2_q` 当作始终存在的主机模式反馈缓存。

## 15. 问题记录：如何读取电机反馈

### 15.1 推荐：在 Linux 主机读取原始 CAN 帧

保持 USB-to-CAN 模式，让主机打开真实 CAN 通道（通常是枚举出来的 `can1`，但应以 `ip link` 的实际映射为准），并确认波特率为 1 Mbps：

```bash
ip link
sudo ip link set can1 down
sudo ip link set can1 type can bitrate 1000000
sudo ip link set can1 up
candump -e -ta can1
```

电机周期发送的反馈帧会直接显示在 `candump` 中。也可以使用 `python-can`：

```python
import can

bus = can.Bus(interface="socketcan", channel="can1")
for msg in bus:
    print(hex(msg.arbitration_id), msg.dlc, msg.data.hex(" "))
```

收到的 8 字节 payload 必须按照具体电机型号的协议手册解码。若使用常见 RM 电机协议，反馈帧通常将角度、转速、电流和温度放在固定字节中，但 ID、缩放系数和有符号性仍需以电机手册为准，不能仅凭本项目的 `Send_RM()` 推断。

### 15.2 在 STM32 固件内部读取

输入 RTT 字符 `c` 进入本地 CAN 模式后，`CAN2_RX_Cplt()` 会收到 `fdcan2` 的帧。当前实现只把 `frame->data` 的 8 字节放入 `basic_can2_q`，`RTT_TX_thread()` 再取到 `uint8_t data[8]` 并打印。因此目前只能看到原始字节，不能知道该帧的 CAN ID，也没有自动得到角度、转速等变量。

如果要在固件中正式解析反馈，应把消息队列元素改成完整的 `struct can_frame`（至少保留 `id`、`dlc` 和 `data`），然后在处理线程中按电机协议解码。例如大端无符号 16 位字段可用：

```cpp
uint16_t raw = ((uint16_t)rx.data[0] << 8) | rx.data[1];
```

同时应移除或重新设计当前 `RTT_TX_thread()` 中收到反馈后固定发送四个零值的测试代码，并避免在回调中用 `k_msgq_purge()` 丢弃历史帧。

## 16. 问题记录：达妙 4340P/4340/4310/8009 反馈解析

达妙电机使用 MIT 等模式时，常见的 8 字节状态反馈布局如下（CAN ID 通常是电机的从机 ID，仍应以该电机配置为准）：

```text
data[0]      高 4 位：错误码；低 4 位：状态/保留信息
data[1..2]   位置 q，16 bit，无符号量化值
data[3..4]   速度 dq，12 bit；data[4] 高 4 位参与速度
data[4..5]   力矩 tau，12 bit；data[4] 低 4 位参与力矩
data[6]      MOS 温度
data[7]      转子温度
```

反量化公式为：

```text
value = raw / (2^bits - 1) * (max - min) + min
```

常见量程参考如下：

| 型号 | 位置范围 | 速度范围 | 力矩范围 |
|---|---:|---:|---:|
| DM4310 | ±12.5 rad | ±30 rad/s | ±10 Nm |
| DM4340 | ±12.5 rad | 需要按电压/版本确认，常见 SDK 为 ±8 或 ±10 rad/s | ±28 Nm |
| DM8009 | ±12.5 rad | ±45 rad/s | ±54 Nm |
| DM4340P | ±12.5 rad | 必须查该型号手册 | 必须查该型号手册 |

不同电压版本或固件版本可能使用不同的速度上限，因此不能把 DM4340 的量程直接套给 DM4340P。`tau` 是估算力矩（Nm），不是未经换算的相电流；若需要电流，应使用电机给出的力矩常数或专用电流字段定义进行换算。

主机侧可以直接解析 `candump` 对应的 SocketCAN 帧：

```python
import can

LIMITS = {
    "DM4310":  (12.5, 30.0, 10.0),
    "DM4340":  (12.5, 10.0, 28.0),  # 具体版本可能是 8.0
    "DM8009":  (12.5, 45.0, 54.0),
    # DM4340P 请替换成厂家手册给出的 vmax、tmax
}

def uint_to_float(raw, low, high, bits):
    return raw / ((1 << bits) - 1) * (high - low) + low

def decode_dm_feedback(msg, pmax, vmax, tmax):
    d = bytes(msg.data)
    if len(d) != 8:
        raise ValueError("达妙反馈帧应为 8 字节")

    err = (d[0] >> 4) & 0x0F
    q_raw = (d[1] << 8) | d[2]
    dq_raw = (d[3] << 4) | (d[4] >> 4)
    tau_raw = ((d[4] & 0x0F) << 8) | d[5]

    return {
        "can_id": msg.arbitration_id,
        "error": err,
        "position_rad": uint_to_float(q_raw, -pmax, pmax, 16),
        "velocity_rad_s": uint_to_float(dq_raw, -vmax, vmax, 12),
        "torque_Nm": uint_to_float(tau_raw, -tmax, tmax, 12),
        "mos_temp_C": d[6],
        "rotor_temp_C": d[7],
    }

bus = can.Bus(interface="socketcan", channel="can1", bitrate=1_000_000)
for msg in bus:
    if msg.arbitration_id == 0x01:  # 按实际电机 ID 修改
        print(decode_dm_feedback(msg, *LIMITS["DM4310"]))
```

项目固件当前只把 payload 放入 `basic_can2_q`，且丢失 CAN ID；如果要在 STM32 内部按多个达妙电机解析，必须把队列元素改为完整的 `struct can_frame`，再使用同样的位提取和反量化公式。

## 17. 代码记录：达妙控制封装

新增的 `inc/Extern_DM.h` 和 `src/Extern_DM.cpp` 与 `Extern_RM` 对称，提供：

- `Send_DM()`：发送达妙 MIT 控制帧；
- `Enable_DM()`、`Disable_DM()`、`Set_Zero_DM()`：发送 `0xFC`、`0xFD`、`0xFE` 命令；
- `Decode_DM()`：将完整 `struct can_frame` 解码为位置、速度、力矩、错误码和温度。

示例（DM4310 的常见量程）：

```cpp
const struct device *can = DEVICE_DT_GET(DT_NODELABEL(fdcan2));

Enable_DM(can, 0x01);
Send_DM(can, 0x01,
        10.0f, 1.0f,       // Kp, Kd
        0.0f, 0.0f, 0.0f,   // 位置、速度、力矩目标
        12.5f, 30.0f, 10.0f);
```

`DM4340P` 的速度/力矩上限必须根据该型号手册传入，不能盲目复用其他型号的量程。新文件已加入 `CMakeLists.txt`，但当前接收队列仍只保存 8 字节 payload；要调用 `Decode_DM()`，还需先让接收队列保存完整 `struct can_frame`。
