# 第 2 课：仓库结构与代码导航

## 课程信息

- 所属模块：模块一，建立项目全局认知
- 建议用时：90～120 分钟
- 前置课程：[第 1 课：项目目标与系统架构](02_第1课_项目目标与系统架构.md)
- 前置要求：知道本项目是 STM32H723 + Zephyr USB-to-CAN 网桥

本课不要求记住所有文件，而是建立一种稳定的阅读方法：面对一个用户动作、一条日志、一个错误码或一帧 CAN 数据，能够迅速找到相关代码，并沿着调用关系继续追踪。

## 1. 本课目标

学完本课后，应能够：

1. 说明项目各个目录的职责。
2. 区分应用代码、头文件、板级硬件描述、构建配置、学习文档和主机工具。
3. 找到项目入口、线程入口、USB 初始化、CAN 启停和电机帧封装的位置。
4. 使用 rg、rg --files、git diff 搜索代码，而不是盲目翻文件。
5. 从一个用户动作反向追踪到具体函数、设备、队列和配置。
6. 区分“定义了某个功能”和“当前固件实际启用了某个功能”。
7. 建立自己的代码导航表和调用链记录。

## 2. 为什么要学习代码导航

嵌入式工程通常不会把一个功能写在一个文件里。例如“主机启动 CAN 通道”至少可能经过：

~~~text
Linux ip link
    ↓
主机 gs_usb 驱动
    ↓ USB 控制请求
Zephyr gs_usb 类
    ↓
can_set_mode() / can_set_bitrate() / can_start()
    ↓
STM32 FDCAN 驱动
~~~

只看 Basic_CAN.cpp，只能看到 CAN API，不知道谁调用它；只看 main.cpp，只能看到 USB 注册，也不知道主机的通道请求如何进入 CAN 驱动。

代码导航要解决三个问题：

1. 功能在哪里声明？例如设备节点在 DTS 中声明，线程入口在头文件中声明，配置开关在 prj.conf 中出现。
2. 功能在哪里实现？例如 CAN 启停在 Basic_CAN.cpp，模式切换在 M_S_Control.cpp，RTT 命令在 K_RTT_Thread.cpp。
3. 功能在哪里使用？例如 Basic_CAN_Start() 在 C_M_TO_S() 中调用，Send_RM() 在 RTT_TX_thread() 中调用。

### 3.5 docs、userpy、Z_SEGGER 和 Tutorial

docs 是已有分析资料：readme.md 记录环境和主机命令；NOTES.md、USB_NOTES.md 记录 CAN、USB 和 Zephyr 笔记；CAN_ANALYSIS*.md 记录延迟、抖动和完整性测试；CHANGELOG.md 记录历史变化。

userpy 保存主机测试和调试工具，例如 CS_CAN.py、CS_CAN_Linux.py、USB_RESET.py 和 pyOCD 配置。它们不是固件代码，但用于复现通信、重新枚举 USB 和测量性能。

Z_SEGGER 保存 J-Link RTT 脚本、Ozone 工程和变量观察扩展。

Tutorial 保存学习过程。根据 AGENTS.md，每课应记录目标、原理、实验、数据、结论和未解决问题。

## 4. 构建关系

打开 CMakeLists.txt，重点查看 target_sources：

~~~cmake
target_sources(app PRIVATE
    src/main.cpp
    src/Basic_USB.cpp
    src/Basic_CAN.cpp
    src/Extern_RM.cpp
    src/K_RTT_Thread.cpp
    src/K_CAN_Thread.cpp
    src/K_USB_CAN_ERR_Thread.cpp
    src/M_S_Control.cpp
)
~~~

由此确认：

1. 这些 cpp 文件会参与应用编译。
2. 源文件被编译，不代表每个函数都会被调用。
3. 线程是否运行不能只看文件是否存在，还要检查 K_THREAD_DEFINE 是否实际启用。
4. target_include_directories 指定了 inc 和 src，代码才能找到项目头文件。

main.cpp 还被单独设置为 -O0 和 -g3，即不优化并保留较多调试信息。做实时性测量时要记录构建选项，因为调试版和优化版可能有时序差异。

~~~bash
rg -n 'CONFIG_USBD|CONFIG_CAN|CONFIG_LOG|CONFIG_THREAD' prj.conf boards
~~~

确认功能是否打开，以及资源大小如何设置。

## 6. 从用户动作反向追踪

每个动作都记录：

~~~text
触发者 → 入口 → 中间函数 → 设备或队列 → 最终效果
~~~

### 6.1 固件启动

从日志 Begin Work 开始：

~~~text
Zephyr 启动
    ↓
main()
    ↓
LOG_INF("Begin Work")
    ↓
can_channels_validate()
    ↓
gs_usb_register()
    ↓
添加 USB 描述符和配置
    ↓
usbd_init()
    ↓
usbd_enable()
~~~

搜索：

~~~bash
rg -n 'Begin Work|can_channels_validate|gs_usb_register|usbd_init|usbd_enable' src inc
~~~

思考：哪一步失败会导致 USB 不使能？can_channels_validate 检查什么？为什么 gs_usb_register 要在 USB enable 前完成？

### 6.2 主机启动 CAN 通道

主机命令可能是：

~~~bash
sudo ip link set can1 type can bitrate 1000000
sudo ip link set can1 up
~~~

它在设备侧大致对应：

~~~text
ip link set can1 up
    ↓
Linux gs_usb 驱动
    ↓ USB MODE(START) 请求
Zephyr gs_usb 类
    ↓
CAN 驱动 can_set_mode() / can_start()
~~~

要与本地模式路径区分：

~~~text
RTT 输入 c
    ↓
RTT_RX_thread()
    ↓
M_S_Control.C_M_TO_S()
    ↓
Basic_CAN_Start()
    ↓
can_add_rx_filter()
can_set_mode()
can_set_bitrate()
can_start()
~~~

两个路径都能启动 CAN，但触发者和管理者不同。

### 6.3 真实 CAN 收到一帧

搜索：

~~~bash
rg -n 'CAN2_RX_Cplt|basic_can2_q|k_msgq_put|k_msgq_get|frame->data' src inc
~~~

当前代码链路：

~~~text
fdcan2 硬件收到 CAN 帧
    ↓ Zephyr CAN 接收回调
CAN2_RX_Cplt()
    ↓
k_msgq_purge(&basic_can2_q)
    ↓
k_msgq_put(&basic_can2_q, frame->data, K_NO_WAIT)
    ↓
RTT_TX_thread()
    ↓
k_msgq_get(&basic_can2_q, data, K_FOREVER)
~~~

重要限制：当前队列元素是 8 字节，不是完整 struct can_frame。队列之后 CAN ID、DLC 和标志已经不可见。

### 6.4 发送 RM 电机命令

搜索：

~~~bash
rg -n 'Send_RM|can_send|Frame\.data|\.dlc|\.id' src inc
~~~

追踪链路：

~~~text
调用者
    ↓
Send_RM()
    ↓
填充 can_frame.id / dlc / data[0..7]
    ↓
can_send()
    ↓
fdcan2 驱动和 CAN 总线
~~~

当前 RTT_TX_thread 在读到 basic_can2_q 数据后，调用 Send_RM，参数为 fdcan2、ID 0x010 和四个零值。这说明线程中存在实验性的固定 RM 命令逻辑，不要仅凭函数名推断它已经实现完整电机协议。

## 9. 实验二：追踪一个符号的完整生命周期

以 basic_can2_q 为例：

~~~bash
rg -n 'basic_can2_q' src inc
~~~

把结果分类：

1. 定义：K_MSGQ_DEFINE(basic_can2_q, 8, 8, 2)。
2. 声明：extern struct k_msgq basic_can2_q。
3. 生产：CAN2_RX_Cplt 中的 k_msgq_put。
4. 消费：RTT_TX_thread 中的 k_msgq_get。
5. 清理：CAN2_RX_Cplt 中的 k_msgq_purge。

完成：

| 项目 | 当前实现 |
|---|---|
| 元素大小 | |
| 队列容量 | |
| 生产者 | |
| 消费者 | |
| 是否主动清空旧数据 | |
| 是否保存 CAN ID | |
| 是否保存时间戳 | |
| 队列写满时的行为 | |

k_msgq_put 使用 K_NO_WAIT，不等待队列空间。队列满时可能立即失败；如果调用者不检查返回值，就可能静默丢帧。

## 10. 实验三：确认“定义”和“启用”的区别

执行：

~~~bash
rg -n -C 2 'K_THREAD_DEFINE|CAN2_tid|USB_CAN_Err_tid' src/main.cpp
~~~

当前可以看到 CAN2_thread 和 USB_CAN_ERR_thread 的实现，但对应线程创建语句被注释。因此：

- 不能因为函数存在，就断定它正在运行。
- 不能因为函数有统计逻辑，就断定统计线程正在执行。
- 判断当前行为时，要同时检查函数定义、线程创建点和条件编译。

再检查配置：

~~~bash
rg -n 'CONFIG_.*=y|CONFIG_.*=n|# CONFIG_' prj.conf boards/H7_Work
~~~

当前功能必须同时满足：

~~~text
源文件被加入构建
    且
相关符号没有被条件编译排除
    且
线程或函数实际被启动
~~~

## 13. 当前仓库中的导航注意事项

### 13.1 文件名不一定代表最终功能

K_USB_CAN_ERR_Thread.cpp 存在，但 USB_CAN_Err_tid 的线程创建被注释，不能把文件存在当作功能启用。

### 13.2 注释可能描述历史状态

CHANGELOG 和旧实验笔记记录了不同日期的行为。阅读历史资料时必须核对当前源码和配置。

### 13.3 头文件宏可能生成全局对象

Basic_USB.h 中的 USBD_*_DEFINE 宏可能生成设备、描述符和相关对象，不只是普通函数声明。

### 13.4 Linux 设备名和 Zephyr 设备名不是同一层

fdcan2 是 STM32 的 DeviceTree/Zephyr 设备；Linux 的 can0、can1 是主机网络设备名，中间还有 USB 通道和主机枚举过程。

### 13.5 payload 不等于完整 CAN 帧

basic_can2_q 传递的是 8 字节数据，不代表原始 CAN 帧只有这些信息。协议分析时还要关注 ID、DLC、flags 和时间戳。

10. 如果修改 CAN 接收数据结构，至少要检查哪些文件？

### 参考要点

1. CMakeLists.txt 描述构建过程和源文件；prj.conf 描述 Zephyr/Kconfig 功能与资源配置。
2. src 放实现；inc 放跨模块使用的声明、类型和接口。
3. 在 src/Basic_USB.cpp；通道 0 是 can_loopback0，通道 1 是 fdcan2。
4. 线程创建宏可能被注释、条件编译排除，或者入口从未被启动。
5. 搜索符号后区分 K_MSGQ_DEFINE、extern、k_msgq_put、k_msgq_get 和 k_msgq_purge。
6. 不等待资源，队列满或 CAN 发送资源不足时可能立即失败；必须检查返回值。
7. 搜索日志文本，再看 LOG_MODULE_REGISTER、所在函数和调用者。
8. can1 是 Linux 主机网络设备名，fdcan2 是 STM32 的 Zephyr/DeviceTree 设备名，中间还有 USB 通道映射。
9. cpp 告诉你行为，h 告诉你接口，DTS 告诉你硬件，prj.conf 告诉你编译和资源条件。
10. Basic_CAN.h/.cpp、消息队列消费者、回调注册位置、相关线程，以及依赖 payload 长度的协议封装代码。
