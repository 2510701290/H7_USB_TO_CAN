# H7_USB_TO_CAN 深度学习路线

## 1. 项目定位

本项目不是传统的“上位机—下位机—电机”三层控制系统，而是一个运行在 STM32H723 上的 USB-to-CAN 网桥：

```text
Linux 主机
  ↓ SocketCAN / python-can / gs_usb
USB Bulk 传输
  ↓
STM32H723 + Zephyr
  ↓
CAN / FDCAN2
  ↓
电机驱动器内部控制器
```

由于没有额外的下位机控制板，Linux 主机承担了更多控制职责。STM32 主要负责 USB 协议转换、CAN 收发、缓存、线程调度和状态切换。因此学习重点应放在“端到端通信链路”和“实时控制系统”，而不是只按文件顺序阅读代码。

## 2. 第一张必须画出的图

先画出“一帧电机命令到达电机，并收到一帧回复”的时序图，并给每一步标注线程、中断、队列、缓冲区和时间戳。

主机发送到电机：

```text
cansend / python-can
    ↓
Linux gs_usb
    ↓ USB OUT
gs_usb_tx_thread
    ↓
can_send()
    ↓
fdcan2
    ↓
电机
```

电机返回主机：

```text
fdcan2 接收中断
    ↓
CAN2_RX_Cplt()
    ↓
basic_can2_q
    ↓
处理线程 / gs_usb RX
    ↓ USB IN
Linux SocketCAN
```

需要能够回答：

- 一帧 CAN 数据在哪里进入系统？
- 哪些代码运行在中断上下文，哪些运行在线程上下文？
- 一帧数据经过了几次复制？
- 哪些位置可能丢帧？
- 谁负责配置 CAN 波特率和启动通道？
- USB 和 CAN 速率不匹配时，数据暂存在哪里？

## 3. 推荐的代码阅读顺序

按下面顺序阅读，先建立整体模型，再深入细节：

1. `boards/H7_Work/H7_Work.dts`：硬件、时钟、USB、FDCAN 和内存布局。
2. `prj.conf`：Zephyr 功能、线程栈、USB/CAN 缓冲区和日志配置。
3. `CMakeLists.txt`：工程构建和源文件组成。
4. `src/main.cpp`：USB 初始化、gs_usb 注册和线程创建。
5. `src/Basic_USB.cpp`：USB 通道、事件和统计计数。
6. `src/M_S_Control.cpp`：主机控制模式与本地 CAN 控制模式的切换。
7. `src/Basic_CAN.cpp`：CAN 启停、过滤器和接收回调。
8. `src/K_RTT_Thread.cpp`：RTT 命令、消息队列和状态数据处理。
9. `src/K_CAN_Thread.cpp`：虚拟回环和 CAN 周期任务。
10. `src/Extern_RM.cpp`：RM 电机命令的 CAN 帧封装。

## 4. 分阶段学习计划

### 阶段一：构建和调试环境

目标：

- 能独立执行 `west build`、烧录和查看 RTT。
- 能解释 `west.yml`、`CMakeLists.txt` 和 `prj.conf`。
- 能定位编译错误、链接错误和启动失败。

练习：

1. 修改一条 `LOG_INF`，重新编译并在 RTT 中确认。
2. 修改线程栈或日志缓冲区，观察内存变化。
3. 使用 `USB_RESET.py`、`lsusb` 和 `ip link` 验证 USB 重新枚举。

建议记录：`Tutorial/01_构建与烧录.md`。

### 阶段二：Zephyr 内核机制

重点学习：

- `K_THREAD_DEFINE`
- `k_sleep`
- `k_msgq`
- `k_sem`
- `atomic_t`
- 日志线程和 deferred logging
- 线程优先级、栈和上下文切换

练习：

1. 修改线程周期，观察日志和 CAN 帧间隔。
2. 调整线程优先级，观察 USB、CAN 和 RTT 的相互影响。
3. 打开线程分析器，记录每个线程的栈使用率。
4. 故意缩小消息队列或线程栈，记录异常表现和错误来源。

建议记录：`Tutorial/02_Zephyr内核.md`。

### 阶段三：DeviceTree、时钟和内存

重点学习 `H7_Work.dts`：

- PLL 和 520 MHz 系统时钟。
- USB 所需的 48 MHz 时钟。
- FDCAN2 引脚、时钟、中断和 Bosch Message RAM。
- `sram0` 的内存范围。
- RTT 非缓存内存区 `RTT_NOCACHE`。
- Cortex-M7 D-Cache 对 DMA/调试缓冲区的影响。

练习：

1. 找出 USB、FDCAN2 和 RTT 的地址、时钟源及中断号。
2. 修改一个安全的日志配置，确认生成的 devicetree 结果。
3. 解释为什么 RTT 缓冲区不能简单放在普通可缓存区域。

建议记录：`Tutorial/03_DeviceTree时钟内存.md`。

### 阶段四：CAN 和 FDCAN

重点学习：

- 标准帧、扩展帧和 CAN ID 仲裁。
- ACK、位填充、错误帧、Error Passive 和 Bus-Off。
- CAN FD、BRS、Nominal Bitrate 和 Data Bitrate。
- 硬件过滤器、RX FIFO、TX FIFO 和接收中断。
- `can_start()`、`can_stop()`、`can_send()` 和回调。

代码重点：

```text
Basic_CAN_Start()
Basic_CAN_Stop()
CAN2_RX_Cplt()
can_add_rx_filter()
can_set_bitrate()
can_set_bitrate_data()
```

实验：

1. 使用 `can_loopback0` 完成虚拟回环。
2. 使用 `fdcan2` 测试 1 Mbps 经典 CAN。
3. 测试 CAN FD 和 5 Mbps 数据段。
4. 测试标准帧、扩展帧和过滤器。
5. 断开总线、改变波特率、拔掉电机，观察错误状态。

主机侧常用命令：

```bash
ip -d -s link show can0 can1
candump -e -ta can0 can1
cansend can0 123#DEADBEEF
cansend can1 123##1.de.ad.be.ef
```

建议记录：`Tutorial/04_CAN与CANFD.md`。

### 阶段五：USB 和 gs_usb

分三层学习：

1. USB 基础：控制传输、批量传输、EP0、IN/OUT、ACK/NAK/STALL、枚举和描述符。
2. Zephyr USB 栈：`usbd_init()`、`usbd_enable()`、描述符、配置和类注册。
3. gs_usb 协议：`HOST_FORMAT`、`DEVICE_CONFIG`、`BITTIMING`、`DATA_BITTIMING`、`MODE` 和 `GET_STATE`。

关键初始化顺序：

```text
gs_usb_register()
→ 添加语言/厂商/产品/序列号描述符
→ 添加 USB configuration
→ 注册 gs_usb class
→ usbd_init()
→ usbd_enable()
```

练习：

1. 使用 `lsusb -v` 查看设备描述符和端点。
2. 观察 Linux 创建 `can0`、`can1` 的过程。
3. 抓取一次枚举和一次 CAN 通道启动过程。
4. 使用 usbmon 或 Wireshark 区分控制传输和批量传输。

建议记录：`Tutorial/05_USB与gs_usb.md`。

### 阶段六：实时性、吞吐量和抖动

不能只看平均延迟，需要统计：

- 平均值
- 中位数
- p95、p99、p99.9
- 最大延迟
- 丢帧数和重复帧数
- CAN 总线负载
- Bus-Off 次数

将端到端延迟拆成：

```text
主机产生命令
→ USB 排队
→ STM32 收到
→ Zephyr 线程处理
→ CAN 排队
→ CAN 总线发送
→ 电机响应
→ USB 返回
→ 主机收到
```

建议记录：`Tutorial/06_数据路径.md` 和 `Tutorial/07_实时性测试.md`。

### 阶段七：可靠性和安全设计

没有下位机时，必须额外设计：

- 指令超时保护。
- 心跳机制。
- USB 断开后的安全动作。
- CAN Bus-Off 恢复策略。
- STM32 重启后的电机状态。
- 主机程序崩溃时的电机停止策略。
- 命令序号、时间戳和最大速度/电流限制。
- 独立急停或硬件使能信号。

必须回答：

```text
如果 Linux 崩溃、USB 拔出、CAN 断线或 STM32 重启，
电机会不会继续执行上一条指令？
如果会，多久后、由谁让它停止？
```

建议记录：`Tutorial/08_安全与故障恢复.md`。

## 5. 当前代码中值得优先研究的问题

### 5.1 接收回调会清空队列

`Basic_CAN.cpp` 的接收回调先调用 `k_msgq_purge()`，这会清空尚未处理的消息。需要判断项目需求是“只保留最新值”还是“每一帧都不能丢”，再决定使用覆盖式缓存、环形缓冲区还是普通消息队列。

### 5.2 队列只保存 8 字节数据

当前队列没有保存 CAN ID、DLC、标准/扩展帧标志、CAN FD/BRS 标志和时间戳。虽然工程开启了 CAN FD，但应用层还没有完整保存 CAN FD 帧信息。建议设计一个包含完整元数据的 `CanMessage` 结构体。

### 5.3 `can_send()` 返回值未处理

`Send_RM()` 使用 `K_NO_WAIT` 发送，但没有检查返回值。应实验并处理发送队列满、设备未启动、Bus-Off、超时等情况。

### 5.4 信号量错误路径

检查 `M_S_Control` 中所有 `k_sem_take()` 和 `k_sem_give()` 的配对关系，特别是获取失败时是否错误地释放了信号量。并发错误通常不会立刻出现，应该通过压力测试验证。

### 5.5 主机直控的安全边界

平均延迟较好不等于系统安全。需要定义命令新鲜度、通信超时、故障恢复和电机安全停止行为，不能假设 USB 或 Linux 会自动替你完成这些工作。

学习目标不是记住函数名称，而是最终能够独立解释：

1. 一条 `cansend` 命令如何到达 STM32 的 FDCAN 外设。
2. 一帧 CAN 数据经过了哪些中断、线程、队列和缓冲区。
3. USB 满载或 CAN 总线繁忙时，数据会在哪里排队或丢失。
4. 为什么会出现约 1 ms 的延迟尖峰。
5. CAN Bus-Off 后系统是否会自动恢复。
6. USB 重新枚举为什么可能需要拔插或执行 `USB_RESET.py`。
7. 当前应用层是否真正支持完整 CAN FD 帧。
8. Linux 主机崩溃时，电机是否能安全停止。

## 8. 最优先的第一个任务

不要先重构代码。先画出完整时序图，并完成一次虚拟回环实验：

```text
发送一帧
→ 接收回调
→ 消息队列
→ 处理线程
→ 输出日志
```

然后给每个步骤增加计数器和时间戳。这个实验会为后续学习 Zephyr、USB、CAN、实时性和安全设计提供统一的观察入口。
