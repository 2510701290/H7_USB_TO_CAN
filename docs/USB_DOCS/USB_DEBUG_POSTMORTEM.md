# 第一部分：为什么一开始不行

## 1.1 最初看到的现象

```
[00:00:00.123] <err> usb_can: usbd_init ret=-5
[00:00:00.124] <err> usb_can: HAL_PCD_Init failed, 1
```
主机侧：`lsusb` 什么都没有，`dmesg` 一片空白。
`R15`（USB 座 D+ 对 GND）实测 **0.031 V** —— 也就是说设备连上拉电阻都没打开。

## 1.2 我最初的三条错误假设

这三条都不是乱猜的，每一条都有"看起来成立"的理由。**问题就在这里**：

| 错误假设 | 当时看起来成立的理由 | 实际情况 |
|---|---|---|
| **A. Zephyr 版本升级改了驱动行为** | `git describe` 是 `v4.5.0-3834-gfbe7a22abed`（main 分支新版本），代码是很早之前写的 | 确实有细微差异（新 HAL 加了超时），但**不是**枚举失败的原因 |
| **B. 硬件问题：RBIAS / VDDA 1.8V / PHY 不出 60MHz** | 万用表量到 PHY 的 VDDA1.8 = 0V，符合"PHY 在睡眠" | VDDA=0V 是真的，但那是**结果**不是**原因**（PHY 确实在睡，因为被写睡了） |
| **C. LQFP100 封装没有真正的 PC2/PC3，必须"打开"模拟开关** | 手册写"PC2 与 PC2_C 经模拟开关分两路"，思路是"我要用数字侧，那就把模拟侧断开" | **方向完全反了**。`0`=闭合=数字可用，`1`=打开=只剩模拟 |

假设 C 是**最致命**的：我按它写了一行代码，主动把唯一能通的路切断了。

## 1.3 五个把我们带偏的"假证据"

这是我复盘时最想记下来的部分 —— **每一条都是"看起来正常"，实际上什么都不能证明**：

### 假证据 1：`BSESVLD = 1`（以为 ULPI 通信正常）
`GOTGCTL` 的 bit19 置位，看起来是"PHY 告诉我 VBUS 有效，所以 ULPI 总线在正常工作"。
**实际**：当 `GOTGCTL.BVALOEN` / `BVALOVAL`（bit6/bit7）被置 1 时（`USB_DevInit` 在
`vbus_sensing_enable == 0` 时会强制置位），`BSESVLD` 是**软件强行写出来的**，与 PHY 无关。

### 假证据 2：60MHz 时钟存在（以为 PHY 醒了）
用 TIM2 外部时钟模式实测 PA5 = **60.005 MHz**，数据漂亮得让人放心。
**实际**：`USB_FlushTxFifo()` 只需要 CK 一根线就能"成功"，60MHz 只证明 PHY 的
时钟输出还活着，**完全不证明 DATA0~7 / DIR / NXT 有任何一根通了**。

### 假证据 3：软件采样 PA5 判频率（假阳性之王）
一开始没有示波器，我用 GPIO 中断/轮询数 PA5 的翻转，得到"大约一半时间高"的结论。
**实际**：60 MHz 下 1 pF 的寄生耦合阻抗约 2.6 kΩ，远小于 MCU 内部上拉 40 kΩ，
**一根完全浮空的线也能读出 50% 占空比**。同理，上拉下拉探测法也是假阳性。

### 假证据 4：多次 `usbd_init()` 都返回 0（以为软件通了）
在 STP 那个修复做了一半的阶段，`usbd_init` 确实返回 0、`usbd_enable` 也返回 0。
**实际**：这些只说明 MCU 内部的 OTG 内核初始化完了，与外部 PHY 是否握手
一根线都没关系。**返回 0 ≠ 能用**。

### 假证据 5：`HAL_PCD_Init failed, 1`
`HAL_StatusTypeDef` 里 `1` 就是 `HAL_ERROR`，**不带任何位置信息**。
它可能失败在 20 个地方中的任何一处。

> **教训：只要一个"证据"不能唯一指向一个结论，它就不能当证据用。**

# 第二部分：后来发现了什么

## 2.1 四个转折点

### 转折点 1：停止看打印，改为直接读寄存器

不再猜，用调试器把关键寄存器全 dump 出来：

```bash
pyocd cmd -t stm32h723xx -c "halt" \
  -c "read32 0x40040000"   # GOTGCTL
  -c "read32 0x40040010"   # GRSTCTL
  -c "read32 0x40040014"   # GINTSTS
  -c "read32 0x58020810"   # GPIOC IDR
  -c "go"
```

看到 `GRSTCTL = 0x80000030`：
- bit31 `AHBIDL=1` → AHB 空闲，内核没卡死
- bit5 `TXFFLSH=1`、bit4 `RXFFLSH=1` → **冲刷标志一直是 1，永远清不掉**

结合 `GOTGCTL` 里 `BVALOEN/BVALOVAL=1`（证明 `USB_DevInit` 已经执行过），
**失败点被唯一确定在 `USB_FlushTxFifo()`**。这一步把范围从"USB 全栈"缩到"一个函数"。

### 转折点 2：翻 USB3300 数据手册，而不是靠经验

`§6.1.9.3 Start-up Protection`：Link 在就绪前必须**先断言 STP**，
否则 PHY 会把数据总线上的随机电平当成 TX CMD，做出**非法寄存器写**
（典型后果：`SuspendM` 被清零 → PHY 立刻睡回去）。

`§6.1.11`：reset 只能在 CLKOUT 有效后撤销，`TSTART = 2.25~3.5 ms`。
而板上 `C39=100nF` + `R25=4.7k` 的 RC 只有 **470 µs** —— 板载复位"太快"。

→ 修复：`usbd_init()` **全程把 PC0(STP) 按住高电平**，初始化结束才交还 AF10；
另外用 PD9 主动打一个 20 ms 的复位脉冲补上板载 RC 不够的部分。

### 转折点 3：`GPIOC IDR = 0x00000000` —— 硬证据

这一条是整件事的钥匙。不管 PHY 状态如何，**MCU 侧读到的 DIR(PC2) 和 NXT(PC3)
恒为 0**，ULPI 就不可能通信一帧。

顺着这条线去查原理图（`docs/原理图/USB2.0高速测试板/`），用 `docs/原理图/netlist3.py` 逐根核对网表，
发现：
```
ULPI_DIR → U5-12 → U2-17 → PC2_C
ULPI_NXT → U5-11 → U2-18 → PC3_C
```
**LQFP100 上只有 `PC2_C` / `PC3_C` 两个焊盘**，数字功能必须让模拟开关**闭合**。

### 转折点 4：把极性改对，一次成功

```c
SYSCFG->PMCR &= ~(SYSCFG_PMCR_PC2SO | SYSCFG_PMCR_PC3SO);   /* 0 = 闭合 */
```
改完立刻：`lsusb` 出现 `1d50:606f`，`Actual device speed 2`（HS）。

## 2.2 三个真根因（全部已修复，别回退）

| # | 根因 | 一句话症状 | 修复位置 |
|---|---|---|---|
| **1** | `SYSCFG->PMCR.PC2SO/PC3SO` 被置 1（打开开关），而 DIR/NXT 只引到 `PC2_C/PC3_C` | `GPIOC IDR = 0`；D+ 无上拉（0.031 V）；主机完全看不到设备 | `usb_ulpi_analog_switch_fixup()` |
| **2** | OTG 初始化期间把 PHY 写睡（USB3300 §6.1.9.3 的非法寄存器写） | `GRSTCTL.TXFFLSH/RXFFLSH` 永远是 1；`usbd_init ret=-5` | `usb_ulpi_phy_wakeup()` 不释放 + `usb_ulpi_phy_stp_release()` 延后 |
| **3** | DTS 写 `maximum-speed = "full-speed"`，而外部 ULPI PHY 只能 HS | 即使枚举成功也只有 FS，或直接失败 | `boards/H7_Work/H7_Work.dts` |

> 附带修复：板载 RC 复位只有 470 µs（< TSTART 3.5 ms）→ `usb_phy_hw_reset()` 用 PD9 补 20 ms。

## 2.3 如果重来，正确的排查顺序

```
① 物理层：D+ 对 GND 电压。      有 1.5k/1.8k 上拉？没有 → 别碰软件，先查 PHY 供电/复位/使能
② PHY 侧：CLKOUT 有 60MHz 吗？  用 TIM2 外部时钟模式数（不要用软件采样猜）
③ 链路侧：GPIOC IDR 的 DIR/NXT 会动吗？恒为 0 → 查引脚映射 / 模拟开关 / 原理图
④ 内核侧：GRSTCTL 的 TXFFLSH/RXFFLSH 能清掉吗？
⑤ 协议侧：GINTSTS 有 USBRST / ENUMDNE 吗？DCTL.SDIS 是否已清？
```

**核心原则：从物理层往协议层走，每一层都有唯一判据。跳过任何一层都会绕远路。**
我这次是先做了 ④⑤（因为软件代码在手边），结果被内核"看起来成功"骗了很久。

# 第三部分：怎样协作能更快定位问题

## 3.1 我最需要的五类信息（按价值排序）

| 优先级 | 信息 | 为什么 | 怎么给 |
|---|---|---|---|
| ★★★★★ | **现象原文，不要转述** | "枚举失败"没法用；`dmesg` 原文能看出是 -71 超时还是根本没插入 | 直接粘终端输出 |
| ★★★★★ | **原理图 / PCB 网表原文件** | 引脚表截图会漏掉 `_C` 后缀这种要命的细节 | 放 `docs/原理图/` 目录，`.SchDoc`/`.PcbDoc` 都行 |
| ★★★★☆ | **最近改了什么** | 换过线、重焊过、升过 Zephyr、改过 DTS —— 90% 的回归都能对上 | 一句话说明即可 |
| ★★★☆☆ | **芯片手册 / 数据手册** | 时序、上电顺序、引脚定义只有手册说了算，不能靠经验 | PDF 放 `芯片文档/` |
| ★★★☆☆ | **硬件可观测状态** | LED 亮不亮、板子有没有发烫、USB 座是 Type-C 还是 micro | 文字描述 |

## 3.2 提供信息时的三条原则

1. **区分「观察」和「推测」。**
   ❌ "PHY 好像没工作" → 我无法判断这是量出来的还是猜的。
   ✅ "PHY 的 pin29(VDDA1.8) 万用表量到 0V" → 可以立刻推理。

2. **告诉我限制条件。**
   ❌ "没时钟"
   ✅ "手头只有万用表，没有示波器，所以 60MHz 我量不了"
   → 我就会改用 TIM2 计数法，而不是让你去借示波器。

3. **主动说"我试过了、不行"。**
   你试过的失败路径能帮我一秒砍掉一大片搜索空间。

## 3.3 分工表：这些事只有你能做

| 任务 | 谁做 | 说明 |
|---|---|---|
| 读寄存器 / 改代码 / 编译烧录 | **我** | 有 pyocd、RTT、构建环境 |
| 焊板子、飞线、拆换器件 | **你** | 物理操作 |
| 万用表通断/电压测量 | **你** | 我读不到表 |
| 看原理图判断"这个网络接到哪" | **共同** | 我可以跑 `netlist3.py` 提网表，但器件实际装没装只有你知道 |
| 插拔线、换 USB 口、换主机 | **你** | |
| 判断"这个现象是不是我刚刚焊坏的" | **你** | |

## 3.4 一次高效求助的模板

```
【现象】<直接粘原始输出：dmesg / RTT / 寄存器值>
【已确认】<万用表量到的电压、通断；LED 状态>
【限制】<有没有示波器；能不能拆板>
【最近改动】<换过线 / 重焊过 U5 / Zephyr 升到 xxx>
【我试过】<改了 xxx，现象变成 yyy>
【手里资料】<原理图 / 手册放在哪个目录>
```

只要这六项齐全，大部分问题我在第一轮就能给出可执行的下一步，
而不是先花三四轮问"这个量了没有"。

# 第四部分：出现什么问题该做什么（速查）

## 4.1 USB 侧

| 症状 | 第一步该做什么 | 判据 |
|---|---|---|
| `usbd_init ret=-5` / `HAL_PCD_Init failed, 1` | 读 `GRSTCTL`(0x40040010) | `TXFFLSH/RXFFLSH` 一直是 1 → 根因 2（STP 没按住） |
| `lsusb` 完全看不到 | 万用表量 USB 座 D+ 对 GND | < 0.3 V → PHY 没给上拉，先查 PHY 供电/复位；≈1.8 V 以上 → 查主机口/线 |
| 只枚举成 full-speed | 检查 DTS | `maximum-speed` 必须是 `"high-speed"`（根因 3） |
| 反复掉线重连（`boot #` 一直涨） | 读 `RCC->RSR` + RTT 里的 `boot #` | 看是 BOR（供电塌）/ IWDG（卡死）/ PIN（复位脚） |
| 枚举成功但 CAN 打不开 | `ip -br link` 有没有 can0/1/2 | 没有 → gs_usb 没注册；有但 DOWN → 检查 `device descriptor read` 是否报错 |
| 之前能用，改完代码就不行了 | 先 `git stash` 或回退一个提交 | 不要同时改两边（软件+硬件），必须单变量 |

## 4.2 CAN 侧

| 症状 | 第一步 | 说明 |
|---|---|---|
| `ip link set can0 up` 失败 | 看 `dmesg` 里的 gs_usb 行 | 通常是 bitrate 不被 PHY 支持 |
| 能 UP 但发不出去（bus-off / 错误计数涨） | 检查总线上有没有第二个节点 | CAN 必须有 ACK，单节点必然报 ACK 错误 |
| `candump` 什么都收不到 | 确认收发双方波特率/采样点完全一致 | FD 帧还要对齐 `dbitrate` |
| 发帧丢包 | 看 `ip -s link show can0` 的 `dropped` | 可能要升 `CONFIG_USBD_GS_USB_POOL_SIZE`（192 → 256） |
| 云台不动 | 检查 `main.cpp` 的 `APP_STANDALONE_CAN_MODE` | `gs_usb` 与 `CAN2_thread` 都独占 `fdcan1`，只能二选一 |

## 4.3 通用排错纪律

1. **一次只改一个变量。** 同时动软件和硬件，出了新现象就判断不出是谁造成的。
2. **先取证，再改代码。** 改之前把"改之前的寄存器值 / 日志"存一份，否则改完无法对比。
3. **不要用"看起来正常"当证据。** 见第一部分 1.3 的五个假证据。
4. **每层都有唯一判据。** 说不出"这个值说明什么"的时候，说明证据还没取到。
5. **绕不过去就查手册。** 时序、上电顺序这类问题，经验不可靠。

# 第五部分：这次沉淀下来的工具（下次直接用）

| 工具 / 命令 | 用途 |
|---|---|
| `pyocd cmd -t stm32h723xx -c "halt" -c "read32 <addr>" -c "go"` | 免改代码读任意寄存器，比加 printk 快十倍 |
| TIM2 外部时钟模式数边沿 | **唯一可靠的软件测频法**，不要用 GPIO 采样猜 |
| `docs/原理图/netlist3.py <SchDoc> <关键字>` | 从 Altium 原理图提网表（几何 BFS + 同名网络合并） |
| `west rtt --runner pyocd` | 后台日志；烧录前记得 `pkill -f "pyocd rtt"` 释放调试器 |
| `git describe` / worktree 是否干净 | 每次求助前先说清楚 Zephyr 版本，避免"版本漂移"背锅 |
